# ZER-575 临时邮箱插件化边界收敛与内核解耦 RFC

- 状态：Accepted
- 日期：2026-08-24
- 关联任务：ZER-575
- 适用版本：v2.9.11

## 1. 背景

临时邮箱插件通过 `TempMailProviderBase` 接入系统。插件负责上游通信，内核负责领取、持久化和统一状态流转。

iCloud Hide My Email 插件的首版邮箱池接入把插件名称、长期别名语义和项目复用规则写入主干。该实现还新增数据库字段和关联表。这样做会让每个新插件都要求修改内核。

本 RFC 收敛插件与内核的边界。目标是让现有插件和后续插件使用同一条接入路径。

## 2. 问题

首版实现存在以下问题：

1. `outlook_web/services/pool.py` 和 `outlook_web/repositories/pool.py` 根据具体插件名称分支。
2. 插件接入新增 `temp_emails.claimed_project_key` 和 `temp_email_project_usage`。
3. 同一套临时邮箱状态机对不同插件使用不同的成功状态。
4. 底层邮箱池承担了长期资产的跨项目复用职责。

这些问题违反开闭原则。它们也扩大了数据库和测试的维护范围。

## 3. 决策

### 3.1 Provider 注册表是唯一能力来源

内核保留 Outlook、IMAP 和兼容别名等固定入口。第三方临时邮箱 Provider 从运行时注册表读取。

`provider` 参数满足以下任一条件时有效：

1. 参数是内置账号 Provider。
2. 参数是现有兼容别名。
3. 参数是运行时已注册的 `TempMailProviderBase` 实现。

新增插件不再修改邮箱池白名单。

### 3.2 邮箱池使用统一插件流程

邮箱池按以下顺序处理领取请求：

1. 在普通账号池中领取。
2. 在 `temp_emails` 中按 Provider 和域名领取。
3. 如果指定的 Provider 已注册且池中无可用邮箱，调用 Provider 工厂创建邮箱。
4. 把创建结果写入 `temp_emails` 并直接标记为 `claimed`。
5. 如果写库失败，根据 `provider_capabilities.delete_mailbox` 决定是否执行尽力回滚。

该流程不检查具体插件名称。

### 3.3 复用现有数据结构

Provider 身份写入现有 `temp_emails.meta_json.provider_name`。Provider 私有标识、游标和能力也继续写入 `meta_json`。

本次不新增数据库版本，不新增专用字段，不新增专用关联表。

### 3.4 统一临时邮箱生命周期

所有临时邮箱返回统一的 `account_type = "temp_mail"`。

`claim-complete` 使用统一状态映射：

| result | pool_status |
| --- | --- |
| `success` | `used` |
| `verification_timeout` | `cooldown` |
| `provider_blocked` | `frozen` |
| `credential_invalid` | `retired` |
| `network_error` | `available` |

插件不能改变内核状态机。

### 3.5 长期资产由上层管理

长期别名的跨项目复用不是临时邮箱池职责。Worker 或 Client 应保存长期资产，并决定何时复用。

该边界避免底层池同时维护一次性资源和长期资产两套语义。

## 4. 插件契约

插件继续继承 `TempMailProviderBase`。邮箱池只依赖以下通用能力：

- `create_mailbox(prefix, domain)`
- `delete_mailbox(mailbox)`
- `provider_name`
- `provider_capabilities`

创建结果必须包含 `success`。成功结果还必须包含 `email`。`meta` 必须是对象或可解析的 JSON 对象。

如果插件声明 `provider_capabilities.delete_mailbox = false`，写库失败时内核不调用删除接口。

## 5. 兼容性

现有 `custom` 和 `gptmail` 参数继续映射到原有 Provider 名称。Cloudflare 动态创建和完成后回收行为保持不变。

`temp_emails` 历史记录继续从 `meta_json.provider_name` 或 `source` 解析 Provider。系统不要求数据迁移。

## 6. 非目标

本 RFC 不处理以下事项：

- Apple 私有协议或 sidecar 的实现。
- 长期别名的配额统计。
- Worker 或 Client 的长期资产模型。
- 插件目录递归加载。
- iCloud 专用前端页面。

## 7. 验收标准

1. `git grep -i "icloud_hme" -- outlook_web` 无结果。
2. 数据库版本保持 v25。
3. `temp_emails` 不包含 `claimed_project_key`。
4. 数据库不包含 `temp_email_project_usage`。
5. 任意已注册 Provider 都能通过统一工厂动态创建并写入 `temp_emails`。
6. 任意插件邮箱在 `result="success"` 后进入 `used`。
7. 写库失败时，回滚行为遵守 Provider capability。
8. `python -m unittest discover -s tests -v` 全部通过。
9. Black、isort 和 Flake8 门禁通过。

## 8. 回退

本改动只调整未合并的 PR 分支。生产数据库没有执行专用迁移，因此不需要数据库降级脚本。

如需回退代码，可以恢复 PR #153 在本 RFC 之前的提交。回退不能重新引入专用数据库表或插件名称分支。
